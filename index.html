Agentic Identity — A Positioning Guide for the Field

Users are moving AI agents out of experiments and into production and asking how to secure them. The conversations are harder than they should be because everyone uses the same handful of words and almost nobody means the same thing by them. Two users can say “we need agent identity” and want two different things. A request that sounds like an identity problem often turns out to be a question about spending, about which data an agent can reach or about what a model is permitted to say in a response. The most common mistake is not technical. It is proposing an approach that was never going to fit the user’s requirement and discovering the mismatch only later, when changing direction costs more.

How to use this guide

This guide lists the phrases users use and explains what each one usually means in practice. For each pattern it states what Vault does and the point at which the pattern stops being the right answer.

Terms are explained where they first appear.

CHAPTER 03 · TERMS

1. The terms used in this guide

These definitions are deliberately plain. The industry uses the terms loosely and that looseness causes confusion in user conversations.

An agent is software that uses a language model to decide what to do next and that can call tools, APIs or other software to carry it out. Its behavior is not fixed in advance. That is what makes it a security concern. A traditional application does the same thing every time it is given the same input. An agent may not.

Which software is “the agent.” People often picture the language model itself. The agent is almost never the model and it is not the chat or desktop application the person types into. It is the surrounding software the user builds and runs: an MCP server, an orchestrator, an agent platform, a coding assistant runtime or a runtime such as Amazon Bedrock AgentCore. The model decides what it wants to do. The surrounding software decides what gets requested. It is the component that talks to Vault. Throughout this guide, “agent” means that software.

The user chooses which component to register. Vault reads the agent from the claim named by actor_claim, which defaults to act.sub. The ceiling policies apply to whichever component that claim names. The component that builds the Rich Authorization Request can be a different one.

A gateway is a server placed in the network path between the software making a request and the system being called, so that every request passes through it. Because it sits in the path, it can hold the real credential on everyone’s behalf, check each request against a set of rules before allowing it and keep a record of what was asked for. A gateway does not run models or tools itself. It forwards each request to whatever does the work and returns the answer. This guide uses two kinds: a model gateway in front of language model providers and a tool gateway in front of the tools and data sources an agent may reach.

Delegation describes an agent acting on behalf of a named person in a way that records both identities, so that afterward it is possible to say which agent acted and for whom. An agent acting on its own behalf, with no person involved, is not delegation.

The subject and actor claims. When a token says that an agent is acting for a person, the person is named in the sub (subject) claim and the agent in the act (actor) claim. RFC 8693 allows a chain to be expressed by nesting one act claim inside another, so that a prior actor appears at act.act. In the specification’s words, “the outermost act claim represents the current actor while nested act claims represent prior actors,” and “the least recent actor is the most deeply nested.” A related claim, may_act, is how an identity provider records that one party is permitted to act on behalf of another.

Attestation is the means by which a platform proves what a running process is and where it is running. Examples include SPIFFE, a Kubernetes service account or an AWS IAM role attached to a workload.

Token exchange is the mechanism defined in RFC 8693 for trading one token for another. It is how a token that names both a person and an agent is produced. The agent sends a request like this to the identity provider’s token endpoint. Parameter names come from RFC 8693 and authorization_details from RFC 9396.

POST /token
grant_type=urn:ietf:params:oauth:grant-type:token-exchange
subject_token=<the person's token>
subject_token_type=urn:ietf:params:oauth:token-type:access_token
actor_token=<the agent's own token>
actor_token_type=urn:ietf:params:oauth:token-type:access_token
audience=https://vault.example.com
authorization_details=[{"type":"vault:path_access","path":"secret/data/support/customer-records","capabilities":["read"]}]

The identity provider returns a token naming the person in sub and the agent in act.

A Rich Authorization Request , defined in RFC 9396, is a structured description of what one specific request is asking for, carried inside the token. It allows a token to say “read this one thing” instead of “read anything this person can read.”

MCP , the Model Context Protocol, is an open protocol for agents to call tools and data sources. A2A, the Agent2Agent protocol, is one emerging standard for agents to discover and call one another.

How the Agentic IAM pieces fit together

Read this subsection first. The six patterns build on the request flow it describes.

Agentic IAM has four parts: Vault acting as an OAuth resource server, the Agent Registry, three authority models and the Rich Authorization Request.

Vault as an OAuth resource server. In this feature the identity provider issues the token. Vault only checks it. The user’s identity provider, such as IBM Verify, Okta or Entra ID, signs a token and gives it to the agent. The agent hands that token to Vault. Vault fetches the identity provider’s public signing keys from the address in its configuration, uses them to confirm the token has not been altered and then reads the fields inside it. Those fields are the claims. The claim named by user_claim, which is sub by default, identifies the person. The claim named by actor_claim, which is act.sub by default, identifies the agent. The OAuth resource server configuration holds the issuer to trust, the address of its keys, the audience the token must be for and those two claim names. Vault supports more than one of these configurations in a namespace, one per identity provider. Each configuration is its own mount in Vault. That matters later for entities and aliases. Vault reads the claim named by unique_id_claim, jti by default, into the audit record. It does not use it for replay protection. A JWT can be presented repeatedly until it expires, in the same way a Vault token can.

The Agent Registry. The registry is the component the feature adds. Vault has always had identity entities, policies and auth methods, but it had no way to record that an entity is an agent and to cap what that agent may ever reach. Someone on the Vault team creates a registry record for each agent, by hand or through Terraform. The record maps to exactly one Vault identity entity and carries ceiling_policies, an optional owner and a description. Registration is mandatory. If the actor claim names an agent with no registry record, Vault rejects the request.

Give the agent its own entity. The registry accepts a record that points at a person’s entity, but that arrangement does not work for delegation. An entity holds one alias per auth mount and the resource server profile is one mount, so the identity store refuses to add the agent’s alias to an entity that already carries the person’s alias. A token naming that agent as actor then cannot be resolved. The one token a shared entity accepts names the person as both subject and actor. In that case the ceiling on the record applies to the person’s own requests and the audit record shows the same entity as subject and actor. Vault also enforces one registry record per entity.

Three authority models. The token the identity provider issues to the agent can take three shapes. Vault treats each differently. In the first, the agent acts on its own and the token names only the agent.

{ "iss": "https://idp.example.com", "aud": "https://vault.example.com",
  "sub": "nightly-report-agent" }

In the second, the agent acts for a person and the token names the person in sub and the agent in act.

{ "iss": "https://idp.example.com", "aud": "https://vault.example.com",
  "sub": "alex.okonkwo@example.com",
  "act": { "sub": "support-assistant-agent" } }

In the third, the agent acts for a person and the token also states what this one call is for.

{ "iss": "https://idp.example.com", "aud": "https://vault.example.com",
  "sub": "alex.okonkwo@example.com",
  "act": { "sub": "support-assistant-agent" },
  "authorization_details": [
    { "type": "vault:path_access",
      "path": "secret/data/support/customer-records",
      "capabilities": ["read"] } ] }

The values are illustrative. Pattern A has a table comparing when each shape fits.

The Rich Authorization Request. The authorization_details block in the third example is the Rich Authorization Request. It lists the Vault path and capabilities this one request needs, using Vault’s vault:path_access type. It can only narrow access. If the person’s policies and the agent’s ceiling do not already allow the path, listing it grants nothing.

The request can be attached to any token the identity provider issues. In practice it appears with the on-behalf-of shape, because that is where narrowing one request is worth the integration work. The identity provider does not decide which Vault path goes in it. It copies into the token whatever the requesting software asked for. The software that knows the path is the execution layer, the MCP server or orchestrator that is about to call Vault. Vault requires the authorization_details claim by default and rejects a token without it unless optional_authorization_details is set to true on the resource server configuration or on the agent’s registry record. The Make RAR optional page describes relaxing it as not recommended and offers it for migrations or for identity providers that cannot produce one. A user who leaves the default in place meets this rejection on the first call.

Following one request through. The steps below trace the on-behalf-of shape. The other two shapes differ at steps 1, 3 and 7. The paragraph after the list says how.

  1. The person signs in to the application through the identity provider and asks the agent to do something that needs a secret from Vault.
  2. The agent asks the identity provider for a token naming the person as sub and itself as act, using the token exchange request shown in section 1. It sends the person’s token, its own token and the Rich Authorization Request for this call. To hold a token of its own the agent first proves its identity to the identity provider. Pattern F covers how.
  3. The identity provider decides whether this agent may act for this person. The standard mechanism is a may_act claim on the person’s token that names the party allowed to act for them, by sub or client_id. An agent that does not match does not receive a token.
  4. The agent sends that token to Vault in the X-Vault-Token header of its request. There is no login call and no separate Vault token.
  5. Vault fetches the identity provider’s keys and confirms the signature. It reads the person’s identifier from sub and the agent’s from act.sub and looks up an entity for each. Both entities have to exist already, each with an alias on the resource server profile. The agent’s entity is created when the agent is onboarded and its registry record points to it. The person’s entity is provisioned in advance. Only the actor’s entity needs a registry record. A person with an alias and policies but no registration is accepted when the actor is registered. A token that names only a subject and no actor is refused unless that subject’s entity is registered.
  6. Vault collects the person’s own policies from their entity and groups, plus the agent’s ceiling policies from its registry record. If the token carries authorization_details, Vault reads that too.
  7. Vault allows the request only if the person’s policies, the ceiling and, where present, the authorization details each permit it.
  8. Vault returns the secret. Where the secrets engine supports it, Vault instead asks that engine to create a fresh credential with a time limit, such as a database login or a cloud access key (see section 4).
  9. Vault writes an audit record naming the person as the entity and the agent under auth.metadata.actor_entity_id and actor_entity_name, with the issuer, the token’s jti and the authorization details alongside.

For the autonomous shape, steps 1 and 3 do not occur and there is no person’s policy set in step 7. Ceilings apply to delegated requests only, so Vault does not apply the ceiling to a token with no actor claim. An autonomous agent is governed by its own entity policies and, where present, the Rich Authorization Request. The registry record still has to exist, because Vault refuses a token whose presenting entity has no registration. For the shape with a Rich Authorization Request, step 7 applies all three limits.

One case that comes up is two agents registered with two different identity providers, for example one in Okta and one in Entra ID, both acting for the same person. Current Vault Enterprise version does not support delegation across two providers. It is currently in development.

What the registry is for. Without a ceiling, an agent acting for a person could do everything that person can. If the person can read production database credentials and manage the PKI mount, so can any agent acting for them. The identity provider decides which agents may act for which people, but it has no knowledge of Vault paths and cannot narrow what the agent reaches once the request arrives.

The ceiling policy is the Vault team’s own limit, set in Vault, on what a given agent can ever touch. It does not depend on how the identity provider is configured or on what the person can do. A ceiling of read on secret/data/support/* means the agent reads support secrets and nothing else, whichever employee it is acting for and however much that employee is allowed to see.

Take an agent whose only job is to store a value for someone to collect later. Its ceiling allows create and update on a set of paths and nothing else, so it can write but cannot read anything, including what it just wrote. If its model is confused or manipulated into attempting a read, Vault refuses because the ceiling never allowed it. In a second case, an employee can reach AWS, PKI and a dozen KV mounts and an agent acting for them has a ceiling covering one mount. The agent’s reach is that one mount and nothing else, whatever the employee could do alone.

The registry also records which entities in an environment are agents, which nothing else in Vault does. Once there are more than a handful, that inventory is useful on its own.

There is another way to bound an agent that does not use the registry. Each tool declares the scopes it needs. A token broker checks the person’s group membership against those scopes before it issues a token. Vault then selects a database role by scope. In that design the tool declarations and the broker enforce the limit. With the registry, Vault enforces it under the Vault team’s control.

When the registry is worth having. The registry fits when the team that runs Vault wants its own limit on what agents reach, separate from what the identity team configures. Where the identity team and the Vault team are separate and have different change processes, the ceiling gives the Vault team a control they own. An agent’s permissions cannot grow past it through a change on the identity provider side that the Vault team never saw. Where one small team runs both, or where every agent is meant to have exactly what its person has, the ceiling is one more record to keep in step with the identity provider and adds little. In that case the pattern is not the right fit and the user should hear that early.

Requirements. Agentic IAM, including the Agent Registry, requires Vault Enterprise current version or later or HCP Vault Dedicated, an identity provider that can issue a token with sub and act through RFC 8693 token exchange, an entity in Vault for the agent linked to its registry record and an entity for every person an agent may act for, in place before the first delegated request. Not every identity provider supports token exchange.

What agentic IAM is not. Agentic IAM is not a model gateway, because it does not see model traffic and cannot limit spend or which models are called. The identity provider issues the delegated token. Vault validates it. The feature does not establish trust between agents. It evaluates the agent presenting the request rather than any earlier agent in a longer chain.

Three phrases that mean different things to different users

Three expressions come up often, and each has more than one meaning. Ask which one the user means before you answer, because answering the wrong one wastes the meeting.

“Agent identity.” Users use this phrase for proof, for governance or for trust. Proof means a way for a running process to show what it is, which is Pattern F. Governance means a record of which agents exist and a cap on each one, which is Pattern A. Trust means one agent being able to check that another is genuine, which is Pattern B. Vendors also put “agent” and “subagent” on products whether or not a model inside them makes decisions. If there is no model, the product is ordinary software with a new name, and none of the agentic patterns apply.

“Agent to agent.” Some users mean a single coordinating agent that hands work to specialists, and others mean agents calling each other directly in arbitrary combinations. The first is well understood and is the shape described in Pattern B. The second has no documented solution. Tell the user that before design starts.

“Guardrails.” The word is used to mean access control, content filtering, spending limits and human approval, sometimes all at once. Establish which the user means before proposing anything.

3. The six patterns

The sections below describe six patterns. Normally a user requirement is one of these or a combination of them.

Each pattern follows the same shape: what it is in plain terms, a worked example, a diagram, the steps involved, what Vault does and what Vault does not do. The last two are stated separately because Vault plays a different role in each pattern. In Pattern C (the AI gateway) and Pattern E (runtime content guardrails), Vault is not the component making the security decision.

Patterns E and F are used together with the others rather than instead of them. Pattern F is the step underneath Patterns A, B, C and D, because a workload has to prove what it is before Vault or an identity provider gives it anything. Pattern E runs alongside whichever of those patterns the user uses and governs what the agent says rather than what it may reach. A user who asks for E or F on its own usually has one of A to D underneath the request.

Patterns A, B and F depend on the order in which tokens are issued and presented, so they are drawn as sequence diagrams, in which each vertical line is one participant and each arrow is one message, numbered from top to bottom in the order they happen. Patterns C, D and E turn on where components sit in relation to one another, so they are drawn as component diagrams with a labeled boundary around anything that shares a trust zone.

CHAPTER 05 · PATTERN A

Pattern A — Governed agent access to Vault

What it is. A person asks an agent to do something that needs a secret from Vault. The agent should not hold that secret permanently and it should not be able to do more on the person’s behalf than the person could do alone. The agent therefore presents Vault with a token that names both the person and itself. Vault applies the person’s policies and the agent’s ceiling together. Section 1 explains how Vault evaluates a delegated request. This section covers when to use the pattern.

There is a confusing regarding the three arrangements. They give different amounts of accountability.

Authority modelWhat the token carriesWhen it fits
AutonomousThe agent’s own name and nobody else’s.Unattended, machine-to-machine work where no individual is accountable for the action. Vault treats the agent as an ordinary entity with its own policies. A registry record is still required. The ceiling on it applies to delegated requests only, so the agent’s own entity policies govern it (section 1). Short token lifetimes keep the exposure small.
On behalf of a personThe person in sub and the agent in act.Work a named person is accountable for, where the agent must never exceed what that person could do alone.
On behalf of a person, with a Rich Authorization RequestThe same, plus authorization_details naming the path and capabilities for this one call.The most restrictive option. It narrows one request below what the person and the agent are already allowed without changing either of their policies. It costs more integration work, so it is usually reserved for high-impact actions and for cases where per-session limits or explicit user consent are required.

All three use the same registry and the same enforcement point. They differ in how much accountability the request carries. A user can use all three, keeping the heavier ones for the requests that warrant them.

The autonomous row is sometimes dismissed as no better than giving the agent an ordinary Vault token. The registry still adds something. It records which entities are agents and Vault refuses tokens from unregistered ones. On the ceiling that view is right. The Agent Registry documentation describes the ceiling for an agent acting for a person. It applies only to that case. For an autonomous agent the controls are its entity policies, a Rich Authorization Request and the token lifetime.

The rest of this section covers the middle row, on behalf of a person, which is the arrangement users ask about most and the one the diagram shows.

A worked example. A support assistant is asked by a named employee to look up a user record. The employee is allowed to see the record. The assistant on its own is allowed to see nothing. The token states that the assistant is acting for that employee on this one request.

How it works, step by step. The person signs in to the application through the user’s identity provider. The agent asks that identity provider for a delegated token naming the person as subject and itself as actor and sends the token to Vault with its request. There is no separate Vault login, because the token is what Vault authenticates. Vault confirms the signature, resolves the person and the agent to their entities, confirms the agent has a registry record and grants whichever is narrowest of the person’s own policies, the agent’s ceiling and, if present, what this request asked for. Vault returns the secret, or, where the secrets engine supports it, creates a fresh credential with a time limit. Section 4 explains why that is the stronger option. The audit record names the person as the entity and the agent under auth.metadata.actor_entity_id and actor_entity_name, alongside the issuer, the token’s jti and the authorization details it carried.

There is one default that will stop a user’s first request if nobody changes it. Vault requires authorization_details in the token unless optional_authorization_details is set to true on the resource server configuration or on the agent’s registry record. The Make RAR optional page describes relaxing it as not recommended and offers it for migrations or for identity providers that cannot produce a Rich Authorization Request. Decide with the user which way they are going before the first request.

Where the credential lands. The diagram shows a credential returning to “the agent.” It should go to the execution layer, meaning the MCP server, orchestrator or runtime. That layer presents the token, uses the credential and returns only the result of the action to the model. The credential never enters the model’s context, because that context is built partly from content the organization does not control and is copied into traces and logs. Knowledge of which Vault path holds which secret also stays in the execution layer (see section 5).

OWASP’s agentic guidance lists an execution layer between the model and the action as a security control. A user who follows that guidance will ask where that layer sits in the design.

What this achieves and what it does not. The execution layer keeps the credential out of the model. Keeping it out of the agent’s process altogether is only partly solved. A separate component has to hold the credential, sit between the agent and the target and speak the target’s protocol. Boundary does this for SSH and RDP through credential injection, where the caller never sees the credential. For targets reached as plain TCP, databases included, Boundary brokers the credential to the caller, so the agent’s process holds it briefly. For arbitrary HTTP APIs there is no equivalent product. Beyond that, the one control left is credential lifetime. Issue the narrowest credential the task needs for the shortest time it needs it and revoke it when the task finishes.

What Vault does here.

Vault validates a token another system issued, acting as an OAuth resource server. It checks that the agent has an Agent Registry record, applies that record’s ceiling alongside the person’s policies, issues the secret or credential and records both identities in the audit log. The registry supplies the ceiling. Vault’s authorization engine makes the decision and requires both the person’s policies and the ceiling to allow the request.

What Vault does not do here.

The identity provider issues the delegated token and decides which agent may act for which person. Vault evaluates only the agent presenting the request. Earlier agents in a chain are not evaluated. Vault also does not decide what business task the agent is doing or which Vault path that task needs. Translating a business intention into a path or role belongs to the user’s MCP server, orchestrator, gateway or agent platform. That same layer usually decides which of the three authority models a request goes out under. Vault enforces whichever arrives.

When this is the right pattern. Use it when an agent needs Vault resources while acting for a named person and the team running Vault wants its own ceiling on what agents reach instead of depending only on what the identity team configures. That separation between two teams is the main argument for the pattern. If it does not exist at the user, the pattern is probably not the right fit.

Where it stops. The documented scope covers an agent acting on its own behalf and a person delegating to an agent. It does not cover trust between agents and it is not a model gateway. It needs Vault Enterprise or HCP Vault Dedicated and an identity provider capable of token exchange.

CHAPTER 06 · PATTERN B

Pattern B — Delegated identity chain between agents

What it is. One agent needs another agent to do part of the work. The first agent should not pass along the token it is holding, because the second agent would then be able to do everything the first one could. Instead, a new token is issued for each hand-off, each narrower than the last, and each one records who is acting for whom.

A worked example. A coordinating assistant is asked to onboard a new joiner. It asks one specialist agent to create the account and a second to arrange system access. Each specialist receives its own token scoped to its own task. The audit trail shows the full sequence of who asked for what.

How it works, step by step. The person signs in and the supervising agent receives a token for them. When the supervisor needs a specialist, it asks the identity provider for a new token scoped to that one specialist and that one task, then calls the specialist with it. The person’s original token never leaves the supervisor. The specialist performs the same exchange again before it touches any real system. Each exchange is a separate decision by the identity provider, so a task the identity provider will not allow is refused before the specialist ever sees it.

What the token carries. Every token in the chain names the person in sub and the agent currently acting in act. When work passes from one agent to the next, the identity provider nests the previous agent’s act inside the new one, so one token carries the full chain with the newest actor on the outside. Anyone reading it afterward can see who asked for what.

The token below is what the second hop of the onboarding example looks like, with illustrative values. The top-level fields are standard JWT claims. act comes from RFC 8693 and authorization_details uses Vault’s own vault:path_access type.

{
  "iss": "https://idp.example.com",
  "aud": "https://vault.example.com",
  "exp": 1789459200,

  "sub": "alex.okonkwo@example.com",

  "act": {
    "sub": "access-provisioner-agent",
    "act": {
      "sub": "onboarding-supervisor-agent"
    }
  },

  "authorization_details": [
    {
      "type": "vault:path_access",
      "path": "database/creds/joiner-provisioning",
      "capabilities": ["read"]
    }
  ]
}

The deeper a claim is nested, the earlier that agent acted.

Vault reads one actor. The actor_claim setting tells Vault which claim to use. It defaults to act.sub, the outermost one. Vault finds that agent’s entity, applies its ceiling and ignores everything nested underneath. The nested agents stay in the token for the identity provider to audit. They change nothing about what Vault allows. Vault authorizes the last hop and the identity provider owns everything before it.

What Vault does here.

Vault does not perform the exchanges. It validates tokens issued elsewhere. Its role comes at the end, when the final agent needs a secret or credential and Vault authorizes that one hop.

What Vault does not do here.

Vault does not create or maintain the chain. It reads one actor from the configured claim and evaluates that agent only. The chain is built, governed and audited at the identity provider, which is also where may_act decides whether one party may act for another.

When this is the right pattern. Use it when agents hand work to one another and the user needs to establish afterward who requested what. That covers one supervisor with specialists as well as agents calling each other.

Where it stops. What works is one coordinating agent calling specialist agents, with each specialist then calling whatever it needs, whether Vault, a database or an internal API. Those are two hops, coordinator to specialist and specialist to the system it acts on. Two further shapes come up in user conversations and neither has a documented answer: specialists calling each other instead of reporting back to the coordinator, and long chains where the original person’s permissions are re-checked at every step. If a user describes either, record the requirement through section 8. Adopting the A2A protocol does not fill the gap on its own. A2A defines how agents describe themselves and exchange tasks. Its enterprise guidance leaves authentication to standard mechanisms such as OAuth 2.0 and OpenID Connect and leaves authorization to the implementer, so who may ask whom to do what is still the user’s design.

Limits to know before designing. Vault does not broker between agents and does not check the chain. It authorizes the hop directly in front of it. Vault’s audit record covers that one hop, so answering which person ultimately caused an action means following the chain of exchanges back across the identity provider’s records until you reach the person. If no person was ever involved, there is nobody to reach. Reconstructing a long chain after the fact is labor-intensive. A user whose compliance case depends on it should know that at design time.

Where the credential lands. The rule from Pattern A applies. Each agent in the chain is an execution layer, its tool or MCP layer presents the token and uses the credential, and only the result comes back to the model.

Whether Vault can be the identity provider for the chain. Users ask this because they would prefer not to set up token exchange on their identity provider. Vault has two features that appear to fit. Neither does. Vault’s OIDC provider lets an application use Vault to sign people in, in the way it might use Okta or Entra ID. It supports one grant type, authorization_code, which needs a browser and a person clicking through a login screen, so one piece of software cannot use it to prove itself to another. Vault’s identity tokens are for machines. A workload that has already logged in to Vault can request a signed JWT naming its Vault entity, and anything that trusts Vault’s published keys can verify it, so one component can prove to another which Vault entity it is. Neither feature mints the nested act chain. Vault’s documented role is to validate tokens issued elsewhere, and no token exchange grant is documented for either feature. Vault can help agents prove who they are, but it does not perform the delegation this pattern depends on. Pattern F describes where identity tokens do fit.

CHAPTER 07 · PATTERN C

Pattern C — An AI gateway for models and tools

What it is. An application or agent calls a language model and calls tools such as MCP servers and databases. Some component has to decide which models a team may use, how much it may spend, which tools it may call and record what it sent. Vault cannot decide any of that because Vault never sees the traffic. Only a component that every request passes through can do that, which is the gateway’s role. It sits in the network path, checks each request against rules and records what was asked for.

In the IBM portfolio that component is IBM DataPower Interact Gateway. It governs calls to language model providers and publishes existing APIs as MCP tools behind one gateway, with token-based rate limiting and traffic policies, so it is the model gateway and the tool gateway in one product. Any gateway that sits in the path and enforces rules fits the pattern. Interact Gateway is the one to lead with.

A worked example. Instead of giving every team the company credit card, each team receives a prepaid card that only works at approved merchants, has a spending limit and itemizes every transaction. The company card stays in the safe.

Why this pattern changed. Until recently, calling a model provider meant holding a long-lived API key. The gateway held that key and Vault gave each project a smaller key that only worked at the gateway. The providers are moving away from the long-lived key. Anthropic supports Workload Identity Federation, in which a workload presents a token its own platform already gives it, such as a Kubernetes service account token or an Azure managed identity. Anthropic returns a token that lasts a few minutes. Azure OpenAI has worked this way through Entra ID for some time. Google Cloud offers API keys bound to a service account for Gemini on Vertex AI. The pattern now has two variants. A user with a mixed estate runs both.

Variant one. The gateway holds a provider key and Vault issues project keys.

The gateway is configured once with the real provider credential, which is stored in Vault and rotated from there where the provider allows it. Each project receives its own key, bound to the models or tools it may use, a budget and a rate limit. Vault issues that key to the workload when it starts, so nobody copies a key into a configuration file. The application calls the gateway instead of the provider. A request for anything outside the project’s allow-list is refused at the gateway, and every request is logged against the project. Use this variant when the provider only accepts a static key or when the callers have no platform identity to present, which is the usual case for virtual machines, CI runners and developer laptops.

Variant two. Workload identity on both sides and no key anywhere.

The application presents its platform identity, for example a Kubernetes service account token, to the gateway. The gateway checks it and applies the same rules as before, then authenticates to the provider by federation, presenting its own platform identity and receiving a short-lived token. There is no project key for Vault to issue and no provider key for the gateway to hold. The gateway does the same job without a stored credential. Use this variant when the provider supports federation and the callers run on a platform that issues them an identity, which means Kubernetes, the major clouds and CI systems such as GitHub Actions.

What Vault does here.

In variant one, Vault holds the provider credential, rotates it where the provider allows and issues the per-project gateway keys at runtime. In variant two, Vault issues nothing for the model call. In both variants Vault issues everything else the same workload needs. The database the application writes to, the internal APIs it calls and the certificate it presents do not accept a workload identity token. They want a username and password, an API key or a certificate. An identity provider cannot give them one. Vault turns the identity the workload already has into the credential each of those systems accepts, for a limited time, with a lease Vault can revoke. Federation removes one credential and the workload still needs the rest.

What Vault does not do here.

The allow-list, the budget, the rate limit and the logging are all enforced by the gateway. Vault enforces none of them. Vault is not the policy decision point in this pattern and should not be presented as one.

How the gateway and Vault divide the work. The gateway decides what the agent is trying to do and Vault decides whether the agent may have the credentials to do it. The gateway owns model routing, tool selection, budgets, rate limits and the record of every call. Vault owns identity, credential issuance and the audit of access to the secrets it holds. Where the user also uses Pattern A, the gateway or orchestrator usually decides which of the three authority models a request goes out under. Vault applies whatever limits the token carries.

When a provider accepts a workload identity directly, users ask why anything should sit in front of it. Federation proves who is calling and nothing more. It does not say which models the caller may use, what it may spend, what it sent or how one rule applies across three providers. A user whose applications call the provider directly either builds those controls into every application or does without them. The gateway is where those controls are enforced whether or not a credential is involved. The providers also authenticate differently from one another. If every application talks to each provider directly, every change is a code change in every application. If the gateway sits in front, the change happens there once.

The Vault MCP server. Vault ships an MCP server that lets an agent read and manage Vault through MCP tool calls. Users find it. Some propose it as the way to give agents credentials, which is the opposite of its purpose. Its documentation states that it can expose Vault data, including secrets, to the connected model and client, that it is for local use only and that it should only run in trusted networks with trusted clients. Putting it behind a shared gateway that serves a desktop AI assistant is what that warning describes.

When this is the right pattern. Use it when the concern is access to models or tools: provider keys held by developers, uncontrolled spending, restricting which models or tools may be used or recording what was sent. Whether the provider supports federation decides which variant to build. It does not decide whether the gateway is needed.

Where it stops. A gateway is only an enforcement point if the caller cannot go around it. Without network controls that stop software from reaching the provider directly, it is a convention rather than a control. The calling software also has to allow its endpoint to be configured, and some tools do not expose that setting, so their traffic never reaches the gateway. Whether the callers are “agents” makes no difference to any of this, because the pattern applies to anything calling a model.

CHAPTER 08 · PATTERN D

Pattern D — A secured development environment for coding agents

What it is. A coding assistant such as Cursor, GitHub Copilot, Claude Code or Windsurf runs on the developer’s laptop with the developer’s own permissions. It can read every configuration file and credential on the machine. It installs packages from the internet when it decides it needs them. It needs a credential for every model and tool it uses, so those credentials end up scattered across the laptop. If it makes a mistake or is tricked into one, nothing on the laptop contains the damage. The mistake happens while the code is being written, before anyone reviews it. This pattern moves the assistant, the source code, the tools and the credentials off the laptop onto managed infrastructure and leaves only the editor behind.

A worked example. A developer opens their normal editor, but the code and the coding assistant are running on managed infrastructure instead of on the laptop. The developer never holds a credential for anything the assistant uses.

How it works, step by step. The developer signs in with existing company SSO. A broker such as Boundary authorizes the session, and because the workspace has no public address, each developer can reach only their own. Vault signs a short-lived certificate for that session. The editor then connects remotely, so the editor is running locally while nothing else is. Credentials are already present inside the workspace, written to memory and not to disk. The agent reaches models and tools only through the gateways described in Pattern C. When the session ends the credentials expire, while the work itself persists.

Vault and the gateways are shared platform services. A single Vault and a single set of gateways serve every developer, which is why the diagram places them in their own zone outside the workspace boundary. The workspace holds no standing credential of its own. It authenticates to Vault and receives what it needs for that session.

What Vault does here.

Vault is the credential authority for the entire environment. It signs the session certificate, issues the source-control token and supplies the model key and the tool token. All of these are short-lived, all are held in memory and not on disk, and each project is kept separate from the others.

What Vault does not do here.

The scheduler runs the workspace, the broker authorizes the connection, the identity provider authenticates the person and the gateways determine what the agent may reach. Vault does none of those.

A stronger variant, where Vault authorizes each request as well as supplying credentials. In the arrangement described so far, Vault issues credentials into the workspace. Users propose two weaker alternatives, handing the coding assistant a Vault token of its own or letting it reuse the developer’s token, and neither is attractive. If the workspace has its own Vault token, then the audit log shows the workspace with no way to tell which developer was behind an action. If the assistant reuses the developer’s token, then the audit log shows the developer with no way to tell whether the person or the assistant acted. Either way the ability to say who was responsible is lost. That loss is worse with an assistant than with ordinary software because its behavior cannot be predicted.

The stronger arrangement applies Pattern A inside the workspace. Instead of holding a standing Vault credential, the coding assistant obtains a delegated token from the organization’s identity provider that represents the developer and optionally carries task-specific constraints as a Rich Authorization Request. The path runs from the developer, through the coding agent, through the MCP server or orchestrator, to the identity provider and only then to Vault. Access is evaluated per request against the developer’s own permissions, the agent’s ceiling policies and, where used, the session’s authorization details. The workspace holds no long-lived Vault credential.

When this is the right pattern. Use it when the concern is coding assistants specifically: what they can reach, what they spend and what source code leaves the organization.

Where it stops. The pattern assumes a human developer working with an assistant. Agents that operate with limited human involvement, that are published to a shared platform and that call one another are a different shape. The pattern does not address identity between agents.

CHAPTER 09 · PATTERN E

Pattern E — Runtime content guardrails

What it is. This pattern governs what is said, where the patterns above govern who is allowed to do what. An agent can be instructed to do something harmful by content it reads, such as a document, a support ticket or a web page. It can also disclose sensitive information in its own responses. Both the incoming request and the outgoing response are therefore inspected before they are allowed to proceed.

A worked example. A user support agent reads a ticket that contains hidden text instructing it to retrieve unrelated user records. The inspection layer recognizes the attempt and blocks the request before the agent acts on it.

How it works, step by step. Traffic traveling to and from the agent passes through an inspection point at the platform layer. Incoming content is checked for injection attempts and unsafe instructions. Outgoing content is checked for sensitive data and masked where required. A policy engine makes the decision, and policy is managed centrally rather than by each application team. The application itself is not modified.

What Vault does here.

Vault supplies the inspection service with the credentials it needs, such as a key for the model it calls or a token for the data source it checks against. The rules live in the policy engine. Vault does not hold them.

What Vault does not do here.

Inspecting content and deciding whether to allow or block it is the policy engine’s job. Vault has no part in that decision.

When this is the right pattern. Use it when the user’s stated concern is about behavior rather than access.

Where it stops. This pattern says nothing about who the agent is or what it is permitted to reach. It complements the identity patterns and does not replace them. A user who needs both should hear that at the start. Detection is probabilistic. Inspection reduces exposure to injected instructions and does not eliminate it, so it should never be presented as a guarantee. That uncertainty is a further reason to keep the access controls in the other patterns in place underneath it.

CHAPTER 10 · PATTERN F

Pattern F — Workload identity

What it is. Before anything else can happen, a running process has to prove what it is, as distinct from who it is acting for. This is the foundation underneath most of the other patterns. It is the pattern most often confused with agent identity.

The distinction that matters most. Workload identity answers which process this is and where it is running. Agent identity answers which agent this is and what it is allowed to do. Ten agents built by 10 different teams, all running in identical containers, look identical to the infrastructure and must not look identical to governance, because they do different jobs and should reach different things. Workload identity admits the process, and agent identity decides what it can do once admitted. When a user says machine identity is not enough for them, this distinction is what they mean.

How it works, step by step. The platform attests the workload, confirming that this is a particular pod, on a particular node, under a particular cloud role. The workload receives a signed identity document as a result. It presents that document to Vault or to the identity provider in order to authenticate. It receives credentials in return, so no long-lived password or key has to be stored in the workload or in its configuration.

What Vault does here.

Vault accepts the platform’s attestation through its Kubernetes, JWT, cloud provider and certificate-based auth methods, then issues Vault credentials in return, which removes the need for a bootstrap secret.

What Vault does not do here.

The platform performs the attestation. Vault only consumes the result. Attestation alone says nothing about what the workload is permitted to do on anyone’s behalf.

Where the agent’s own identity comes from. In the delegated flow of Pattern A the agent never logs in to Vault separately. It presents the token the identity provider gave it and Vault authenticates that token. The agent had to prove itself to the identity provider before it could get that token. That earlier step is easy to miss. The workload identity problem arises between the agent and its identity provider rather than between the agent and Vault.

There are four ways to solve it, in two groups. Options 1 and 2 establish a workload’s identity from scratch. Options 3 and 4 take an identity Vault has already accepted and repackage it so another system can verify it.

Option 1. Let the platform vouch for it. Kubernetes can prove that a pod is a particular pod. AWS, Azure and Google can prove a workload runs under a particular role. Vault’s Kubernetes, JWT, cloud and certificate auth methods accept that proof directly, with nothing extra to install.

Option 2. Use SPIFFE, with Vault accepting the identity. If the user already runs SPIRE, it inspects each workload and issues it an SVID, a short-lived identity document. Vault Enterprise’s SPIFFE auth method accepts those. The SPIFFE auth method page states that “Vault is the consumer, not an issuer of the SVID,” so SPIRE has to issue it first. Vault takes certificate-based SVIDs and checks them against a configured trust bundle. It takes JWT-based SVIDs and checks them against that bundle’s published keys.

Option 3. Use SPIFFE, with Vault issuing the identity. If the user does not run SPIRE and does not want to, Vault Enterprise’s SPIFFE secrets engine can issue SVIDs itself. The workload logs in to Vault using whatever auth method it already has, then asks Vault for an SVID. The engine issues JWT-based SVIDs only. For certificate-based identity the SPIFFE secrets engine page points to the PKI secrets engine.

Option 4. Use Vault identity tokens. A workload that has already logged in to Vault can ask for a signed JWT naming its Vault entity, and anything that trusts Vault can verify it against keys Vault publishes. Use this when a workload needs to prove to a third system which Vault entity it is.

If the third system is a model provider, how it fetches keys matters. Anthropic’s Workload Identity Federation fetches an issuer’s keys over public HTTPS on port 443. An internal Vault cannot serve them, so it has to be registered with its keys pasted in. Anthropic does not refresh that inline registration, so every Vault signing key rotation stops the exchange until someone updates the keys by hand.

The reason to choose identity tokens over the platform’s own identity is the claims they can carry. A Kubernetes service account token or a cloud role proves what the workload is and carries nothing else. A Vault identity token can carry entitlements from the entity’s metadata and group membership, such as which models the workload may use or which business unit it belongs to. A gateway or a provider’s federation rule can act on those. Okta can add the same claims to a client credentials token itself. Entra largely cannot for an application-only token, so the difference is larger for Entra users. An identity provider that supports token exchange can be configured to accept a Vault-signed JWT as the agent’s actor token.

Choosing between them. Users usually frame this as SPIFFE or Vault. That framing is wrong. The four options are not four versions of the same thing. Options 1 and 2 start from nothing, because the platform or SPIRE inspects the running workload and vouches for it. No credential needs to exist beforehand. Options 3 and 4 need the workload to log in to Vault first, which means something else already established its identity. They repackage that identity so other systems can check it. They are useful, but they do not answer the original question of how the workload proves itself the first time. The question is where the first proof should happen. Choose SPIFFE if the user runs a mix of Kubernetes, virtual machines and cloud services, wants one consistent way to identify workloads across all of it and will take on running SPIRE. Choose the platform’s own auth method if Vault is already deployed and the user would prefer not to operate another system. If one of their workloads then needs to prove itself to something outside Vault, use option 3 or 4 to give it a token that system can check. Both SPIFFE options need Vault Enterprise.

When this is the right pattern. Use it when an agent must prove what it is in order to obtain its own credentials, which is nearly always the case underneath one of the other patterns.

Where it stops. All of this proves what a process is. None of it says what the process may do. If two different agents run in identical containers, then every method above returns the same answer, that this is a legitimate workload on this platform, and nothing here says that the first agent handles payroll and the second handles support tickets or that they should reach different secrets. The Agent Registry and ceiling policies in Pattern A supply that distinction.

CHAPTER 11 · CROSS-CUTTING

4. Capabilities that appear across more than one pattern

Three requirements come up often enough to be mistaken for patterns in their own right. They are better understood as capabilities used within the patterns above.

Human approval for sensitive actions. Someone approves a high-impact action before it goes ahead. The two ways to do it are owned by different teams. That ownership often decides which one a user adopts.

The first happens at the identity provider, usually through CIBA (Client-Initiated Backchannel Authentication). In practice the person receives a notification on a registered device and taps to approve or deny. It answers whether this individual approves. The identity team configures and runs it. CIBA is an optional part of the OpenID Connect family, so not every identity provider implements it. IBM Verify supports it, and so does Okta, though Okta’s documentation states that web applications are the only application type its CIBA flow supports. Other providers do not implement it or implement it only in certain editions. Which identity provider the user runs decides whether this route exists.

The second is Vault’s own Control Groups. They answer whether this specific request, against this specific path, is approved. The team that runs Vault configures them. When a request hits a Control Group requirement, Vault returns a wrapping token instead of the secret. The requester has to get that token’s accessor to the people who must approve. They approve it in Vault and only then can the requester unwrap and get the data. The Control Groups documentation describes no built-in way to notify approvers, so the requester has to reach them by some other means. That makes Control Groups a sensible fit for planned administrative work, such as rotating root keys or regenerating recovery keys, where everyone involved already knows it is happening. It is an awkward fit for approving an agent’s individual request while the agent waits. A design that uses Control Groups for agent requests has to supply the notification and the wait itself.

Whichever route is used, the approval prompt should be generated from the exact request being authorized rather than from descriptive text supplied by the application, so that what the person approves is what they grant.

Attribution and audit. Attribution is the ability to answer, after something has happened, which agent did it, for which person and under what authority. There is nothing to switch on, because it comes automatically wherever a token carries both identities, which means the on-behalf-of arrangements in Pattern A and the chained version in Pattern B. The other patterns produce Vault audit logs as normal with no second identity to record, because no delegation is involved. The autonomous model in Pattern A has no person in the token, so it can answer which agent but never for whom. A user who chooses the autonomous model gives up the ability to answer “for whom.” State that trade-off when they choose it.

Dynamic credentials and their lifecycle. Instead of storing a credential and handing out copies, Vault can create one at the moment it is needed and destroy it afterward. A database user comes from the database secrets engine, a cloud access key from a cloud secrets engine such as the AWS secrets engine and a certificate from PKI. Dynamic credentials are more important for agents than for conventional software, because an agent’s behavior is not fixed in advance and shortening the life of the credential is one of the few controls that does not depend on predicting what the agent will do. It comes up in three of the patterns. In Pattern A Vault hands a credential to an agent, in Pattern D it issues credentials into a developer workspace and in Pattern F a workload receives credentials after proving what it is. The other three patterns never have Vault issue a credential to anything.

Every such credential is issued against a lease. The lease is what answers the question users ask next: what happens when an agent is compromised, or when the person it was acting for leaves. Revoking the lease invalidates the credential itself instead of merely withdrawing permission to fetch it again, and revocation can be applied to a whole tree of leases at once. Ask any user planning to run a large number of agents how they intend to offboard one, because the answer shows how far they have thought the lifecycle through.
